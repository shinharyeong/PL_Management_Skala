# 도메인 규칙

조직별 재무 엑셀 제출, 금액 수정 소명, 손익 Gap, 버전, master에 관한 업무 규칙입니다. 설계 v0.2 · 2026-11-16의 합의를 반영했습니다. 상세 컬럼·불변조건은 [논리 ERD](development/erd.md), 현재 파서와 서비스 적재·승인의 경계는 [DB 매핑](development/db-mapping.md)을 따릅니다. API 0.9-draft는 전체 39개 중 36개 경로와 V1~V5를 구현하며 연간 확정·수정/Gap 소명·월간 승인 마스터까지 연결합니다. 실제 실행 검증 결과는 [로컬 환경](development/local-environment.md)에 별도로 기록합니다.

## 1. 용어

| 용어 | 뜻 |
| --- | --- |
| 경영기획 담당자 | 제출을 요청하고, 소명을 검토하고, 승인하는 본사 담당자 |
| 조직 담당자 | 각 조직의 엑셀을 제출하고 소명을 작성하는 담당자 |
| 연간 계획 | 연초에 조직이 제출해 확정한 월별 계획 값 |
| 실적 | 매달 조직이 제출하는 해당 월의 실제 값 |
| 추정 | 실적 제출 시 함께 받는 **다음 달부터 12월까지**의 예상 값 |
| 손익 | 확인된 영업이익(OP) = 총매출 − 총영업비용. 현재 손익 Gap 적용 대상 |
| 직전 버전 | 같은 달 첫 제출은 이전 달 마지막 제출 완료본, 재제출은 같은 요청의 직전 제출 완료 회차. 반려본 포함, DRAFT·실패 업로드 제외 |
| 계획 대비 Gap | 해당 월 실적 손익 − 연간 계획의 같은 월 손익 |
| 직전 대비 Gap | 이번 제출본의 값 − 직전 버전의 같은 칸 값 (실적·추정 모두) |
| 소명 | 원천 금액 수정 또는 OP Gap 기준 초과에 대해 제출 전에 작성하는 설명. 보고 항목·연월·시나리오마다 하나의 검토 흐름 |
| 제출본 | 조직의 전체 스냅샷. 작성 중에는 DRAFT이며 최종 제출 때 회차 부여 |
| master | 한 달의 모든 조직 승인본을 합친 전사 최종 정답표 |
| Contingency | 승인된 조직 계획 합산 후, 경영기획팀이 전사 단위로 떼어두는 예비분 |
| 보고 영업이익 | 합산 영업이익 − Contingency. 원본 답안지의 "Contingency 제외 영업이익"과 같은 값으로, 연초 보고 기준 |

> 파서 코드의 `gap_relationships`(영업이익·Contingency 관계)는 이 문서의 Gap과 다른 개념입니다.

## 2. 전체 흐름

1. **연간 계획 수집·확정:** 요청 → 조직 전체 파일 업로드 → 최초 계획은 수정 소명 없이, 재제출은 변경 금액 소명 후 검토 → 전 조직 승인 시 연간 PLAN 마스터 자동 발행 → 기획자가 별도 명령으로 승인 계획본과 명시적 Contingency를 함께 확정·잠금
2. **월 실적 제출:** 경영기획 담당자가 요청 → 조직이 업로드 (해당 월 실적 + 다음 달~12월 추정)
3. **업로드 검사:** 파일명·조직·열린 요청 확인 → DRAFT 파싱·전체 범위 검증 → 원천 금액 수정 감지·OP Gap 계산 → 검토 대상 표시
4. **조직 작성:** 필요한 소명 작성 → 비교본·계획본·기준 재확인 → 회차 부여·제출 완료. 원천 금액 구성까지 같은 수용 소명만 이어받음
5. **경영기획 검토:** 소명별로 수용 또는 재요청 → 재요청된 소명은 조직이 다시 작성 → 모두 수용되면 승인, 제출본 자체가 잘못되면 재제출 요청
6. **master 생성·갱신:** 최초 전 조직 승인 후 생성. 이후 새 승인 조직만 참조를 교체하고 나머지 조직의 기존 승인본을 유지 → 홈 화면 반영
7. **조회·보고:** 고정된 PLAN/ACTUAL 마스터의 표·차트와 계획 대비 값 조회. 별도 보고 데이터 생성 API와 파일 내보내기는 후속 범위

## 3. 제출과 버전

### 제출 요청

- 연간 계획과 월 실적 모두 **경영기획 담당자의 요청으로 시작**합니다. 조직이 먼저 제출할 수 없습니다.
- 요청이 대상 기간(예: 2026년 연간 계획, 2026년 3월 실적)을 정합니다. 조직은 열린 요청에 대해서만 업로드합니다.
- 업로드는 **열린 요청이 있고, 검토 대기 제출본이 없을 때만** 가능합니다.
- 재제출 요청을 받은 조직은 **그 요청에 대한 재제출만** 올릴 수 있습니다.
- 요청 시 해당 기간의 모든 조직을 필수 대상으로 고정합니다. 일부 조직에 재요청해도 대상 집합을 줄이지 않습니다.
- 최초 제출과 재제출 모두 전체 스냅샷입니다. 일부 행만 기존 제출본에 덧붙이거나 덮어쓰는 방식은 지원하지 않습니다.

### 파일 이름

업로드할 때 **파일 이름 규칙을 가장 먼저 검사**합니다. 맞지 않으면 파싱하지 않고 거부합니다.

| 구분 | 업로드 파일 이름 | 저장 이름 (시스템이 회차 부여) |
| --- | --- | --- |
| 월 실적 | `{조직코드}_YYYY-MM.xlsx` 예) `D100_2026-02.xlsx` | `D100_2026-02-02.xlsx` |
| 연간 계획 | `{조직코드}_YYYY-PLAN.xlsx` 예) `D100_2026-PLAN.xlsx` | `D100_2026-PLAN-01.xlsx` |

- `{조직코드}`가 업로드한 조직 담당자의 조직과 같아야 합니다.
- `YYYY-MM`(또는 `YYYY-PLAN`)이 열린 제출 요청의 대상 기간과 같아야 합니다.
- 표시용 버전 이름과 원본 저장 참조를 구분합니다. 현재 원본은 DB stored_object에 보존하며 S3는 아직 연결하지 않았습니다. 운영 객체 저장 경로는 별도 결정합니다.

### 버전 번호

조직별 월간 버전은 `YYYY-MM-NN`, 연간 계획은 `YYYY-PLAN-NN` 형식으로 표시합니다. 백엔드가 최종 제출 트랜잭션에서 회차를 부여하며, DRAFT에는 확정 회차가 없습니다. 파일 안에 버전을 쓰지 않으며 원본 저장 참조와 표시용 파일 이름을 구분합니다.

```
2025-01-01   1월 첫 제출
2025-01-02   1월 재제출
2025-02-01   2월 첫 제출
```

- `YYYY-MM`: 제출 대상 월
- `NN`: 해당 월의 제출 회차. 재제출할 때마다 1씩 증가
- 버전은 **제출할 때만** 올라갑니다. 소명 작성·재요청이나 승인으로는 바뀌지 않습니다.

### 제출 상태

| 상태 | 뜻 | 다음 제출 가능 |
| --- | --- | --- |
| 작성 중 (DRAFT) | 파싱·검증·필수 소명 준비 단계, 회차 없음 | 최종 검증 후 제출 가능 |
| 검토 대기 (PENDING) | 제출 완료, 경영기획 검토·소명 재요청 진행 중 | 불가 |
| 재제출 요청 | 경영기획 담당자가 반려 | 그 요청에 대한 재제출만 가능 |
| 승인 | 검토 완료, 아카이브됨 | 가능 |

- 조직당 **검토 대기 제출본은 최대 1개**입니다. 승인되거나 재제출 요청을 받기 전에는 다음 버전을 업로드할 수 없습니다.

## 4. 금액 수정과 손익 Gap

이미 제출한 원천 금액이 바뀌면 **기준 금액·비율 이하라도 소명이 필수**입니다. 같은 보고 항목 안에서 원천 증감이 상쇄되어 합계가 같아도 수정입니다. 수정 소명과 OP Gap은 `review_item`·`gap_comparison`·`review_explanation`으로 처리하고 별도 변경 사유 흐름을 두지 않습니다.

수정은 직전 제출본에 존재하는 같은 연월·시나리오의 원천 금액을 비교합니다. 새 달 ACTUAL을 이전 ESTIMATE의 수정으로 자동 간주하지 않습니다. 행 순서·셀 이동만으로 수정이라고 판단하지 않으며 필수 누락을 0이나 허용된 삭제로 취급하지 않습니다. 반려본도 직전 비교에 포함하고 마지막 승인본으로 임의 대체하지 않습니다.

### 손익 Gap 비교 대상

아래 비교는 확인된 OP에 적용합니다. 매출·비용 보고 항목의 원천 금액 수정은 위 규칙으로 따로 감지합니다.

| 대상 칸 | 계획 대비 Gap (vs 연간 계획) | 직전 대비 Gap (vs 직전 버전) |
| --- | --- | --- |
| 해당 월 실적 | ✅ | 같은 달 재제출일 때만 ✅ |
| 추정 (다음 달~12월) | — | ✅ 직전 버전의 같은 월 추정. 1월 첫 제출은 연간 계획 |
| 과거 달 실적 (파일에 함께 들어 있는 값) | — | ✅ |

**예시**

| 제출본 | 직전 버전 | 비교 |
| --- | --- | --- |
| `2026-01-01` | 없음 | 1월 실적 vs 계획, 2~12월 추정 vs 계획 |
| `2026-02-01` | 1월 마지막 버전 | 2월 실적 vs 계획 / 3~12월 추정·1월 실적 vs 1월 마지막 버전 |
| `2026-02-02` | `2026-02-01` | 2월 실적 vs 계획 **그리고** vs `2026-02-01` / 3~12월 추정·1월 실적 vs `2026-02-01` |

- 해가 바뀌면 1월 첫 제출의 추정은 **새해 연간 계획**과 비교합니다.
- 연간 PLAN에는 손익 Gap 기준을 적용하지 않습니다. 최초 계획은 비교본이 없어 수정 소명도 없으며, 확정 전 재제출의 변경 금액은 수정 소명 대상입니다.
- 2월 이후 필요한 직전 비교본이나 비교값이 없으면 제출을 차단합니다. 임의로 연간 계획이나 0으로 대체하지 않습니다.

### 계산

조직·보고 항목·연월·시나리오를 검토 단위로 삼고, 현재 확인된 손익 Gap은 영업이익(OP)에 적용합니다. 매출은 관리분류, 비용은 실적집계기준으로 보고 항목을 연결합니다. 팀·과제·계정 코드는 원천 상세로 보존하며 임의로 매출·비용 계정을 짝지어 손익 항목을 만들지 않습니다. 누적 비교는 하지 않습니다.

자동 계산된 OP가 변했다는 이유만으로 수정 소명을 중복 요구하지 않습니다. 원천 매출·비용 항목에서 수정 소명을 받고 OP가 기준을 초과하면 OP 검토 건을 만듭니다.

```
Gap   = 이번 손익 − 비교 대상 손익
Gap률 = Gap ÷ |비교 대상 손익| × 100
```

### 기준

- **실적 칸과 추정 칸의 기준을 따로** 설정합니다. 예) 실적 ±5%·1천만 원, 추정 ±10%·5천만 원
- % 기준과 금액 기준을 **모두 엄격하게 초과(>)**해야 기준 초과입니다. 경계와 같은 값은 초과가 아니며 표시용 반올림 전 십진값으로 판정합니다.
- **비교 대상 값이 0인 경우:** 이번 값이 0이 아니면 기준과 관계없이 기준 초과로 봅니다. Gap률 대신 "기준 없음"으로 표시합니다.

### 기준 설정 UI

- 현재 화면은 경영기획 담당자가 실적·추정 기준을 각각 **정확한 십진 숫자로 입력**하고 **영향 미리보기**를 눌러 최근 제출 완료본의 초과 건수·조직 수·평가 제외 사유를 확인합니다. 최초 기준을 자동 생성하지 않으며 미설정은 null로 표시합니다.
- 슬라이더·로그 눈금·드래그 중 실시간 미리보기는 후속 UI 제안입니다. 현재 입력·미리보기만으로 기준이 저장되지는 않습니다.
- **적용**을 눌러야 새 기준 이력이 저장되며, **이후 최종 제출부터** 적용됩니다. DRAFT 작성 중 비교본·계획본·기준이 바뀌면 재계산하고 필수 소명을 다시 확인합니다. 제출 완료 후에는 기준을 소급 변경하지 않습니다.

### 소명

- 수정 또는 OP Gap으로 생성한 보고 항목·연월·시나리오별 검토 건에 **소명 하나**를 작성해야 제출할 수 있습니다. 경영기획 담당자가 먼저 요청하지 않습니다.
- 한 칸이 계획 대비·직전 대비 둘 다 넘어도 소명은 하나이며, 걸린 비교를 태그로 붙입니다.

  ```
  D100_2026-02-02 · 2월 · 영업이익(OP) · 실적 · [계획 대비] [직전 대비]
  계획 1,000 / 직전 1,200 → 이번 1,350
  소명: ...
  ```

- **이어받기:** 같은 조직·보고 항목·연월·시나리오의 원천 금액 구성까지 같고 이전 소명이 수용된 경우만 허용합니다. 합계가 같은 상쇄 변경은 이어받지 않습니다. 원본 소명의 참조·답변·수용 메타데이터를 보존합니다. 변경/Gap 없이 이어받기만 한 항목은 작성 필요 건수에서 제외합니다.

### 검토

| 경영기획 판단 | 처리 |
| --- | --- |
| 소명이 적절함 | 수용 |
| 소명이 부족함 | **소명 재요청** (사유 첨부) → 조직이 파일 재업로드 없이 그 소명만 다시 작성 → 다시 검토. 버전은 그대로 |
| 제출본 자체가 잘못됨 | 재제출 요청 |

- 모든 필수 검토 항목에 답변이 있고 마지막 회차가 수용되어야 승인할 수 있습니다. 필수 항목이 없으면 이 소명 조건은 충족합니다. 승인·반려·재요청은 같은 제출본의 상태를 잠금 아래 재확인합니다.
- 수용된 소명은 소명 모음과 조직별 현황(해당 버전 옆)에 남습니다.

## 5. Contingency

- 연간 계획을 확정할 때 경영기획 담당자가 **전사 단위로 한 번** 입력합니다. 조직별로 배분하지 않습니다.
- 입력 후 연간 계획과 함께 잠기며, 연중에 수정하지 않습니다. 연간 계획 자체도 확정 후 연중 수정하지 않습니다.
- 연간 확정 시 조직별 최종 승인 계획본을 `request_target.confirmed_plan_submission_id`에 함께 고정합니다. 확정 이후 요청 재개방·새 제출·채택 계획본 교체를 금지하고 월간 비교는 이 고정본만 사용합니다.
- 조직별 Gap은 조직 계획과 조직 실적의 비교이므로 Contingency와 무관합니다.
- 현재 홈은 합산 영업이익과 확정된 전사 연간 Contingency를 구분해 보여줍니다. 월별·누적 실적에서 연간 Contingency를 임의로 차감하거나 배분하지 않습니다. `합산 영업이익 − Contingency`의 연간 보고 영업이익을 포함한 별도 보고 데이터 구성·내보내기는 후속 범위입니다.
- 원본 답안지의 "Contingency 제외 영업이익"은 보고 영업이익(합산 − Contingency)입니다. 파서는 이 항목을 `OP_EX_CONTINGENCY`로 식별합니다.

## 6. master

- **최초 생성:** 해당 월 요청에 고정된 **모든 조직의 유효한 승인본**이 필요합니다. 한 조직이라도 미제출이거나 최신 제출 완료본이 검토 대기·재제출 요청 상태면 생성하지 않습니다.
  - 생성 전에는 홈 화면에 해당 월을 `master 미생성 (승인 N/M 조직)`으로 표시하고, 미승인 조직 목록을 보여줍니다.
- **버전:** 조직 제출본과 같은 `master-YYYY-MM-NN` 형식을 씁니다.

  ```
  master-2025-01-01   1월 첫 master
  master-2025-01-02   1월 값이 바뀐 승인본 반영
  ```

- **갱신:** 조직 제출본이 **승인될 때** 변경된 ACTUAL 월마다 이전 `master_source` 전체 집합을 복사하고 해당 조직의 새 승인본 참조만 교체합니다.
  - 다른 조직의 새 제출본이 검토 대기·재제출 요청 중이어도 이전 master의 승인본 참조를 유지합니다.
  - 이후 월 제출본이 과거 ACTUAL을 바꾸면 해당 과거 월도 갱신합니다. 반영하는 조직·월은 전체 스냅샷이어야 하며 일부 행만 포함하면 완전성 오류입니다.
  - 기존 master가 없던 월은 최초 생성 조건을 충족해야 합니다. 후속 교체로 이 조건을 우회하지 않습니다.
  - 변경 판정은 OP 총액뿐 아니라 보고 항목별 매출·비용과 원천 금액 구성을 비교합니다. 상쇄 변경도 새 버전을 만들고, 행 위치·파일명·소명만 바뀌거나 숫자·구성이 같으면 기존 master를 유지합니다.
- 이전 master는 덮어쓰지 않고 보존합니다. 승인·영향 월 발행은 원자적으로 처리하고, 같은 월 동시 승인의 중복·누락 발행을 방지합니다.
- 소명은 숫자를 바꾸지 않으므로 master 버전에 영향을 주지 않습니다.
- 홈 화면(전사 손익 현황)은 각 월의 최신 master를 보여주고, 연·월 필터로 이전 master를 볼 수 있습니다. **추정은 홈 화면에 반영하지 않습니다.**
- 보고서에는 생성에 사용한 master 버전을 함께 기록합니다.

### 연간 계획 마스터

홈은 계획 보기와 월 실적 보기를 구분한다. 계획 보기는 연간 PLAN 마스터의 전사·조직·월/연간 합계, 실적 보기는 발행된 ACTUAL 월 마스터와 확정 PLAN의 같은 월 비교를 사용한다. 실제 마스터가 없으면 승인 N/M과 미승인 조직을 표시하고 금액을 0이나 PLAN으로 대신 만들지 않는다. 추정·전년 대비·매출총이익·순이익도 근거 없이 생성하지 않는다.

- 연간 PLAN 요청의 제외되지 않은 전 사업조직 최신 제출 완료본이 APPROVED가 되면 마지막 승인과 함께 연간 계획 마스터를 자동 발행한다. 버전은 `master-YYYY-PLAN-NN`이다.
- 발행 이후 일부 조직만 새로 승인되면 그 조직의 전체 연간 스냅샷만 교체하고 다른 조직은 직전 마스터의 승인본을 유지한다. 금액·상세 구성 지문이 같으면 발행하지 않는다.
- 금액을 별도 복제하지 않고 `annual_master_source`로 불변 제출본을 고정한다. 승인·발행은 원자적이며 과거 버전은 변경하지 않는다.
- 연간 마스터 발행과 연간 계획 확정은 별개다. 발행은 COLLECTING 상태나 Contingency를 바꾸지 않는다. 기획자가 별도 연간 확정 명령을 실행하면 최신 승인 계획본·Contingency를 고정하고 그 기준으로 월간 요청과 ACTUAL 마스터를 처리한다.
- local,demo 환경에서는 17개 사업조직만 활성화한다. D100/D200의 조직·사용자·제출 이력은 삭제하지 않고 비활성화하며, 아직 확정·발행하지 않은 수집 요청에서만 `request_target.excluded=true`로 제외한다. 이는 체험 대상 정정이며 일반 업무 중 필수 조직을 임의로 축소할 수 있다는 규칙이 아니다.

## 7. 역할과 권한

시스템 사용자는 두 역할입니다. CFO·경영진 보고는 업무 흐름에는 있지만 시스템 밖에서 이루어지며, 별도 조회자 역할을 두지 않습니다.

| 역할 | 할 수 있는 것 | 볼 수 있는 제출 기록 |
| --- | --- | --- |
| 경영기획 담당자 | 제출 요청, Gap 기준 설정(실적·추정별), 소명 수용·재요청, 승인·재제출 요청, Contingency 입력 | 전체 조직의 제출 기록 |
| 조직 담당자 | 엑셀 업로드, 소명 작성 | 본인 조직의 제출 기록 |

- 경영기획 담당자는 여러 명일 수 있으며, 모두 전체 조직을 봅니다. 담당 조직을 나누지 않습니다.
- 조직 담당자는 다른 조직의 제출 기록을 볼 수 없습니다.

## 8. 알림

알림은 아래 이벤트와 발송 책임을 설계 범위로 둡니다. 현재 0.9의 업무 API 연결이 실제 알림 발송 구현을 뜻하지 않으며 메일·Slack 등 발송 수단은 후속 범위입니다.

| 이벤트 | 받는 사람 |
| --- | --- |
| 연간 계획·월 실적 제출 요청 | 조직 담당자 |
| 제출 완료 (소명 포함) | 경영기획 담당자 |
| 재제출 요청 | 조직 담당자 |
| 소명 재요청 | 조직 담당자 |
| 재요청 소명 작성 완료 | 경영기획 담당자 |
| 제출본 승인 | 조직 담당자 |
| 마감 리마인드 (미제출·미승인) | 조직 담당자 |

- 후속 알림 구현에서는 업무 이벤트와 발송 인터페이스를 분리합니다.
- 발송 실패가 제출·승인 등 업무 처리를 막지 않습니다.
