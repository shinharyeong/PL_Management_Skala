# 도메인 규칙

조직별 재무 엑셀 제출, 비교·소명, 승인과 마스터의 업무 규칙입니다. 2026-11-18 지정 PRD v8.5와 두 소명 방식 지원 요청을 적용했습니다. 신규 검증의 검토 정책은 `2.0`, 기존 제출의 고정 문맥은 `legacy/1.0` 또는 `1.0`로 보존합니다. 구현 계약은 [API 명세](development/api-contract.md), 구조는 [ERD](development/erd.md), 화면 대조는 [PRD·와이어프레임 대응](development/prd-wireframe-alignment.md)을 따릅니다.

## 1. 용어

| 용어 | 뜻 |
| --- | --- |
| 경영기획 담당자 | 제출을 요청하고, 소명을 검토하고, 승인하는 본사 담당자 |
| 조직 담당자 | 각 조직의 엑셀을 제출하고 소명을 작성하는 담당자 |
| 연간 계획 | 연초에 조직이 제출해 확정한 월별 계획 값 |
| 실적 | 매달 조직이 제출하는 해당 월의 실제 값 |
| 추정 | 실적 제출 시 함께 받는 **다음 달부터 12월까지**의 예상 값 |
| 손익 | 확인된 영업이익(OP) = 총매출 − 총영업비용. Gap은 매출·비용·OP 보고 항목별로 판정 |
| 직전 버전 | 새 달 첫 제출은 전월 마지막 승인본. 같은 요청 재제출은 직전 완료 회차(반려본 포함). DRAFT·실패 업로드 제외 |
| 계획 대비 Gap | 해당 월 실적 손익 − 연간 계획의 같은 월 손익 |
| 직전 대비 Gap | 이번 제출본의 값 − 직전 버전의 같은 칸 값 (실적·추정 모두) |
| 소명 | 보고 항목별 Gap 기준 초과 또는 기획팀의 명시적 요청에 대해 작성하는 설명. 보고 항목·연월·시나리오마다 하나의 검토 흐름 |
| 제출본 | 조직의 전체 스냅샷. 작성 중에는 DRAFT이며 최종 제출 때 회차 부여 |
| master | 한 달의 모든 조직 승인본을 합친 전사 최종 정답표 |
| Contingency | 승인된 조직 계획 합산 후, 경영기획팀이 전사 단위로 떼어두는 예비분 |
| 보고 영업이익 | 합산 영업이익 − Contingency. 원본 답안지의 "Contingency 제외 영업이익"과 같은 값으로, 연초 보고 기준 |

> 파서 코드의 `gap_relationships`(영업이익·Contingency 관계)는 이 문서의 Gap과 다른 개념입니다.

## 2. 전체 흐름

1. **연간 계획 수집·확정:** 요청 → 조직 전체 파일 업로드 → 최초 계획은 기준 없이 검증하고, 재제출은 변경 내역을 비교·검토 → 전 조직 승인 시 연간 PLAN 마스터 자동 발행 → 기획자가 별도 명령으로 승인 계획본과 명시적 Contingency를 함께 확정·잠금
2. **월 실적 제출:** 경영기획 담당자가 요청 → 조직이 업로드 (해당 월 실적 + 다음 달~12월 추정)
3. **업로드 검사:** 파일명·조직·열린 요청 확인 → DRAFT 파싱·전체 범위 검증 → 원천 금액 수정 감지·보고 항목별 Gap 계산 → 검토 대상 표시
4. **조직 작성:** 필요한 소명 작성 → 비교본·계획본·기준 재확인 → 회차 부여·제출 완료. 원천 금액 구성까지 같은 수용 소명만 이어받음
5. **경영기획 검토:** 소명별로 수용 또는 재요청 → 재요청된 소명은 조직이 다시 작성 → 모두 수용되면 승인, 제출본 자체가 잘못되면 재제출 요청
6. **master 생성·갱신:** 최초 전 조직 승인 후 생성. 이후 새 승인 조직만 참조를 교체하고 나머지 조직의 기존 승인본을 유지 → 홈 화면 반영
7. **조회·보고:** 고정된 PLAN/ACTUAL 마스터의 표·차트와 계획 대비 값 조회. 공식 마스터·버전 비교 Excel 다운로드 제공. PDF/수동 자료 틀·기간/조직/지표별 블록 작성·명시 적용·불변 버전·HTML 내보내기 제공

## 3. 제출과 버전

### 제출 요청

- 연간 계획과 월 실적 모두 **경영기획 담당자의 요청으로 시작**합니다. 조직이 먼저 제출할 수 없습니다.
- 요청이 대상 기간(예: 2026년 연간 계획, 2026년 3월 실적)을 정합니다. 조직은 열린 요청에 대해서만 업로드합니다.
- 업로드는 **해당 조직에 선택 발송된 열린 요청이 있고, 같은 요청·조직의 검토 대기본이 없을 때** 가능합니다.
- 반려된 요청의 재제출과 다른 기간의 열린 요청을 병행할 수 있습니다. 다른 요청의 PENDING·REJECTED만으로 새 작업을 막지 않습니다.
- 전사 마스터의 필수 조직 집합은 고정합니다. `organizationIds`로 실제 발송 조직을 선택하고, 아직 선택하지 않은 조직은 같은 요청의 PATCH로 추가 발송합니다. 발송 선택으로 마스터의 필수 조직을 줄이지 않습니다.
- 최초 제출과 재제출 모두 전체 스냅샷입니다. 일부 행만 기존 제출본에 덧붙이거나 덮어쓰는 방식은 지원하지 않습니다.

### 원본 오류 확인과 재업로드

- 누락 금액·유효하지 않은 코드·중복 상세·합계 불일치 등 확인이 필요한 내용은 **조직 담당자가 원본에서 판단하고 수정**합니다. 시스템은 확인한 시트·셀·월과 사유를 안내하며, 정확한 셀이 불명확하면 임의 주소를 표시하지 않습니다.
- 파서는 빈 금액을 0으로 채우거나 코드·조직을 추측해 바꾸지 않습니다. 중복·수정 행 중 하나를 임의로 선택하거나 원본 수식·저장 캐시를 정답에 맞춰 고치지 않습니다. 원본 근거가 확인된 숫자 형식·단위 정규화는 원문과 근거를 보존하며 수행합니다.
- 담당자는 수정하지 않은 항목까지 포함한 **전체 파일을 새로 업로드**하고 파싱·업무 검증을 다시 거칩니다. 이전 파일과 진단은 해당 초안의 근거로 보존하며, 새 업로드가 기존 원본을 덮어쓰지 않습니다.
- 필수 값이 미확정이거나 차단 오류가 남아 있으면 최종 제출·승인·공식 마스터 반영이 불가합니다. 금액 변경·Gap 소명은 별도 업무 절차이며, 소명을 작성했다고 원본 오류가 해소된 것으로 취급하지 않습니다. 경고만 있는 경우에는 서버의 제출 준비 상태를 따릅니다.
- 파서 비교 실험의 기술 마스터가 사용하는 중복·개정 선택은 서비스 제출의 자동 보정 규칙이 아닙니다. 서비스에서는 담당자가 확인한 파일을 제출해야 합니다.

### 파일 이름

업로드할 때 **파일 이름 규칙을 가장 먼저 검사**합니다. 맞지 않으면 파싱하지 않고 거부합니다.

| 구분 | 업로드 파일 이름 | 저장 이름 (시스템이 회차 부여) |
| --- | --- | --- |
| 월 실적 | `{조직코드}_YYYY-MM.xlsx` 예) `D100_2026-02.xlsx` | `D100_2026-02-02.xlsx` |
| 연간 계획 | `{조직코드}_YYYY-PLAN.xlsx` 예) `D100_2026-PLAN.xlsx` | `D100_2026-PLAN-01.xlsx` |

- `{조직코드}`가 업로드한 조직 담당자의 조직과 같아야 합니다.
- `YYYY-MM`(또는 `YYYY-PLAN`)이 열린 제출 요청의 대상 기간과 같아야 합니다.
- 표시용 버전 이름과 원본 저장 참조를 구분합니다. 현재 원본은 DB stored_object에 보존하며 S3는 아직 연결하지 않았습니다. 운영 객체 저장 경로는 별도 결정합니다.

### 버전 번호

조직별 월간 버전은 `YYYY-MM-NN`, 연간 계획은 `YYYY-PLAN-NN` 형식으로 표시합니다. 백엔드가 최종 제출 트랜잭션에서 회차를 부여하며, DRAFT에는 확정 회차가 없습니다. 파일 안에 버전을 쓰지 않으며 원본 저장 참조와 표시용 파일 이름을 구분합니다.

```
2025-01-01   1월 첫 제출
2025-01-02   1월 재제출
2025-02-01   2월 첫 제출
```

- `YYYY-MM`: 제출 대상 월
- `NN`: 해당 월의 제출 회차. 재제출할 때마다 1씩 증가
- 버전은 **제출할 때만** 올라갑니다. 소명 작성·재요청이나 승인으로는 바뀌지 않습니다.

### 제출 상태

| 상태 | 뜻 | 다음 제출 가능 |
| --- | --- | --- |
| 작성 중 (DRAFT) | 파싱·검증·필수 소명 준비 단계, 회차 없음 | 최종 검증 후 제출 가능 |
| 검토 대기 (PENDING) | 제출 완료, 경영기획 검토·소명 재요청 진행 중 | 불가 |
| 재제출 요청 | 경영기획 담당자가 반려 | 해당 요청에 재제출 가능. 다른 기간 작업도 가능 |
| 승인 | 검토 완료, 아카이브됨 | 가능 |

- **같은 요청·조직의 검토 대기본은 최대 1개**입니다. 다른 요청·기간의 검토 대기본은 병행할 수 있습니다.

## 4. 항목별 비교·Gap·소명

### 신규 검증 정책 2.0

- 비교 단위는 조직·보고 항목·연월·시나리오입니다. 매출·비용·OP를 각각 비교하며 임의의 매출/비용 계정 짝을 만들지 않습니다. 팀·과제·셀 주소는 원천 근거로 보존합니다.
- 실적 vs 확정 계획, 추정 vs 확정 계획, 추정 vs 직전 동일 월 추정을 지원합니다. 1월 첫 제출은 이후 추정을 연간 계획과 비교합니다.
- 새 달의 직전 기준은 **전월 마지막 승인본**입니다. 같은 요청 재제출은 직전 제출 완료 회차를 사용하여 반려된 파일과도 비교합니다. 필수 비교값이 없으면 오류를 표시하며 0으로 대체하지 않습니다.
- 원천 금액 구성 변경은 기준 이하·상쇄 변경도 감지하지만, `GAP_ONLY`는 변경만으로 필수 처리하지 않고 Gap 초과·명시 요청을 필수로 합니다. `ALL_CHANGES`는 이 조건에 원천 금액 변경도 더합니다. 연간 PLAN 최초 제출에는 비교 기준과 자동 Gap 소명이 없습니다.
- `Gap = 현재값 − 비교값`, `Gap률 = Gap / |비교값| × 100`. 원 금액은 정밀 십진수이며 화면용 반올림 값으로 판정하지 않습니다.
- 차이율·최소 금액을 각각 켜고 끌 수 있습니다. 최소 하나를 켜야 하며 둘 다 켜면 두 조건을 모두 엄격히 초과해야 합니다. 비교값이 0이면 비율은 산정 불가이고, 금액 조건이 켜져 있으면 그 조건도 만족해야 합니다.
- 현재 실적 5%·1천만 원, 추정 10%·5천만 원은 저장된 초기 운영값입니다. 기준 변경은 새 이력이며 작성 중 초안은 재검증합니다. 이미 제출된 비교 문맥을 소급 변경하지 않습니다.

### 검토 단계와 소명 회차

`검토 필요 → 검토 대상 선정 → 소명 진행중 → 재검토 → 소명 승인 완료` 흐름과 `제외됨` 상태를 구분합니다. 기획팀은 PENDING 제출의 항목을 선택·제외하거나 기한·메시지를 포함해 일괄 소명을 요청합니다. 제외는 사유를 반드시 기록하고 필수 작성·승인 대기 집계에서 제외합니다. 승인된 제출의 비교·금액은 변경하지 않습니다.

한 항목이 여러 비교 기준을 넘더라도 소명은 항목·연월·시나리오별 한 흐름입니다. 보완 요청은 새 소명 회차를 만들고 제출 버전이나 숫자를 바꾸지 않습니다. 원인·향후 대응을 답변에 적고 PDF/XLSX/PNG/JPEG 근거를 회차별로 첨부할 수 있습니다. 첨부 원문은 덮어쓰지 않으며 과거 회차는 조회·다운로드만 가능합니다.

소명 수락은 설명을 수용하는 행위이며 마스터 금액을 변경하지 않습니다. **제출 승인**은 별도 명령입니다. 제외되지 않은 필수 소명이 모두 수용되고 원본·금액 검증 차단 사유가 없어야 승인할 수 있습니다. 제출본 오류는 반려하여 전체 파일 재제출을 요청합니다.

같은 조직·보고 항목·연월·시나리오의 원천 금액 구성까지 같고 이전 답변이 수용됐을 때만 이어받습니다. 원본 소명 참조와 회차 메타데이터를 남기며 합계가 같은 상쇄 변경에는 자동 이어받기를 하지 않습니다.

### 기존 제출 이력

기존 `1.0`/`legacy/1.0` 검증은 모든 원천 금액 변경의 필수 소명과 OP 중심 비교를 보존합니다. 과거 제출·승인·마스터를 재작성하지 않습니다. 새 초안의 명시적 검증부터 2.0을 적용합니다. 사용자가 고른 다른 버전과의 비교 조회·Excel 내보내기는 소명 기준이나 마스터를 변경하지 않습니다.

## 5. Contingency

- 연간 계획을 확정할 때 경영기획 담당자가 **전사 단위로 한 번** 입력합니다. 조직별로 배분하지 않습니다.
- 입력 후 연간 계획과 함께 잠기며, 연중에 수정하지 않습니다. 연간 계획 자체도 확정 후 연중 수정하지 않습니다.
- 연간 확정 시 조직별 최종 승인 계획본을 `request_target.confirmed_plan_submission_id`에 함께 고정합니다. 확정 이후 요청 재개방·새 제출·채택 계획본 교체를 금지하고 월간 비교는 이 고정본만 사용합니다.
- 조직별 Gap은 조직 계획과 조직 실적의 비교이므로 Contingency와 무관합니다.
- 현재 홈은 합산 영업이익과 확정된 전사 연간 Contingency를 구분해 보여줍니다. 월별·누적 실적에서 연간 Contingency를 임의로 차감하거나 배분하지 않습니다. `합산 영업이익 − Contingency`의 연간 보고 영업이익을 포함한 별도 보고 데이터 구성·내보내기는 후속 범위입니다.
- 원본 답안지의 "Contingency 제외 영업이익"은 보고 영업이익(합산 − Contingency)입니다. 파서는 이 항목을 `OP_EX_CONTINGENCY`로 식별합니다.

## 6. master

- **최초 생성:** 해당 월 요청에 고정된 **모든 조직의 유효한 승인본**이 필요합니다. 한 조직이라도 미제출이거나 최신 제출 완료본이 검토 대기·재제출 요청 상태면 생성하지 않습니다.
  - 생성 전에는 홈 화면에 해당 월을 `master 미생성 (승인 N/M 조직)`으로 표시하고, 미승인 조직 목록을 보여줍니다.
- **버전:** 조직 제출본과 같은 `master-YYYY-MM-NN` 형식을 씁니다.

  ```
  master-2025-01-01   1월 첫 master
  master-2025-01-02   1월 값이 바뀐 승인본 반영
  ```

- **갱신:** 조직 제출본이 **승인될 때** 변경된 ACTUAL 월마다 이전 `master_source` 전체 집합을 복사하고 해당 조직의 새 승인본 참조만 교체합니다.
  - 다른 조직의 새 제출본이 검토 대기·재제출 요청 중이어도 이전 master의 승인본 참조를 유지합니다.
  - 이후 월 제출본이 과거 ACTUAL을 바꾸면 해당 과거 월도 갱신합니다. 반영하는 조직·월은 전체 스냅샷이어야 하며 일부 행만 포함하면 완전성 오류입니다.
  - 기존 master가 없던 월은 최초 생성 조건을 충족해야 합니다. 후속 교체로 이 조건을 우회하지 않습니다.
  - 변경 판정은 OP 총액뿐 아니라 보고 항목별 매출·비용과 원천 금액 구성을 비교합니다. 상쇄 변경도 새 버전을 만들고, 행 위치·파일명·소명만 바뀌거나 숫자·구성이 같으면 기존 master를 유지합니다.
- 이전 master는 덮어쓰지 않고 보존합니다. 승인·영향 월 발행은 원자적으로 처리하고, 같은 월 동시 승인의 중복·누락 발행을 방지합니다.
- 소명은 숫자를 바꾸지 않으므로 master 버전에 영향을 주지 않습니다.
- 홈 화면(전사 손익 현황)은 각 월의 최신 master를 보여주고, 연·월 필터로 이전 master를 볼 수 있습니다. **추정은 홈 화면에 반영하지 않습니다.**
- 보고서에는 생성에 사용한 master 버전을 함께 기록합니다.

### 연간 계획 마스터

홈은 계획 보기와 월 실적 보기를 구분한다. 계획 보기는 연간 PLAN 마스터의 전사·조직·월/연간 합계, 실적 보기는 발행된 ACTUAL 월 마스터와 확정 PLAN의 같은 월 비교를 사용한다. 실제 마스터가 없으면 승인 N/M과 미승인 조직을 표시하고 금액을 0이나 PLAN으로 대신 만들지 않는다. 추정·전년 대비·매출총이익·순이익도 근거 없이 생성하지 않는다.

- 연간 PLAN 요청의 제외되지 않은 전 사업조직 최신 제출 완료본이 APPROVED가 되면 마지막 승인과 함께 연간 계획 마스터를 자동 발행한다. 버전은 `master-YYYY-PLAN-NN`이다.
- 발행 이후 일부 조직만 새로 승인되면 그 조직의 전체 연간 스냅샷만 교체하고 다른 조직은 직전 마스터의 승인본을 유지한다. 금액·상세 구성 지문이 같으면 발행하지 않는다.
- 금액을 별도 복제하지 않고 `annual_master_source`로 불변 제출본을 고정한다. 승인·발행은 원자적이며 과거 버전은 변경하지 않는다.
- 연간 마스터 발행과 연간 계획 확정은 별개다. 발행은 COLLECTING 상태나 Contingency를 바꾸지 않는다. 기획자가 별도 연간 확정 명령을 실행하면 최신 승인 계획본·Contingency를 고정하고 그 기준으로 월간 요청과 ACTUAL 마스터를 처리한다.
- local,demo 환경에서는 17개 사업조직만 활성화한다. D100/D200의 조직·사용자·제출 이력은 삭제하지 않고 비활성화하며, 아직 확정·발행하지 않은 수집 요청에서만 `request_target.excluded=true`로 제외한다. 이는 체험 대상 정정이며 일반 업무 중 필수 조직을 임의로 축소할 수 있다는 규칙이 아니다.

## 7. 역할과 권한

시스템 사용자는 두 역할입니다. CFO·경영진 보고는 업무 흐름에는 있지만 시스템 밖에서 이루어지며, 별도 조회자 역할을 두지 않습니다.

| 역할 | 할 수 있는 것 | 볼 수 있는 제출 기록 |
| --- | --- | --- |
| 경영기획 담당자 | 제출 요청, Gap 기준 설정(실적·추정별), 소명 수용·재요청, 승인·재제출 요청, Contingency 입력 | 전체 조직의 제출 기록 |
| 조직 담당자 | 엑셀 업로드, 소명 작성 | 본인 조직의 제출 기록 |

- 경영기획 담당자는 여러 명일 수 있으며, 모두 전체 조직을 봅니다. 담당 조직을 나누지 않습니다.
- 조직 담당자는 다른 조직의 제출 기록을 볼 수 없습니다.

인앱 알림은 실제 제출·최신 소명 회신·기한 경과를 조회하여 날짜별로 표시하고 사용자별 읽음을 저장합니다. 메일·Slack 등 외부 발송은 구현하지 않았습니다. 로그인 코드도 local·demo의 로컬 수신함에서만 확인하며 실제 사내 메일 발송·운영 인증은 별도 연결이 필요합니다.

## 2026-11-18 설정·소명 모드·보고 작성

- 전역 소명 규칙은 `GAP_ONLY` 또는 `ALL_CHANGES`다. 둘 다 Gap 초과·명시 요청을 포함하고 ALL_CHANGES는 연간 PLAN을 포함한 원천 금액 변경도 필수로 한다. 제외 항목은 필수에서 뺀다. 현재 설정을 제출 완료본에 소급 적용하지 않고 검증 문맥·검토 항목에 저장한다. 설정이 바뀐 초안은 재검증해야 제출할 수 있다.
- 조직·담당자·역할·요청 메시지를 이력과 함께 관리한다. 최초 로그인 및 소속·역할 변경 후 서버 기준으로 다시 확인한다. 조직 변경이 과거 요청의 필수 대상 집합을 바꾸지 않는다.
- 제출 반려는 전체 메모와 선택 항목의 원천 좌표·기준/현재 금액·사유 스냅샷을 보존한다. 임의 비교에서 요청한 소명은 별도 회차의 비교 문맥으로 보관하여 기존 자동 Gap 기준을 유지한다.
- 보고 자료의 PLAN은 확정 계획, ACTUAL은 공식 마스터를 우선한다. 승인/대기 제출을 대체 원천으로 쓸 때는 잠정 표시하며 전체 조직·기간 누락을 부분 전사 합계로 표시하지 않는다. PREVIOUS는 전월 승인본에 있는 같은 대상 월 추정이다.
- 보고 사유는 수락 소명만 사용하고 보고 기준 기여액으로 배분한다. 말단 유형 배분·상위 합계·기타(미분류)를 구분한다. OP 기여는 매출 증가(+), 비용 증가(−)이며 같은 범위의 OP 소명과 상세 소명을 중복 더하지 않는다. 숫자·원문은 AI가 재작성하지 않는다.
- 보고 미리보기는 30분 제안이다. 적용 버튼만 자료의 새 버전을 생성하고 복원도 이전 내용을 새 버전으로 저장한다. 자료틀·SQL·분류표·자료의 과거 버전은 보존한다.
