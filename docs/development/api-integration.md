# 공개 API와 실행 프론트 연결

## 적용 범위와 판정 기준

기준은 develop `5366fa8`과 이슈 #57·#62·#63 수정 작업이다. `docs/api/openapi.yaml`의
method+path를 백엔드 `@RestController` 경로와 비교했다. 변수 이름만 정규화했을 때
공개 경로는 양쪽 모두 **67개**이며 차집합은 없다. 이는 경로 존재 확인이며 모든 DTO와
업무 동작의 통합 테스트를 의미하지 않는다.

프론트는 `frontend/src/main.js` → `prototype/main.js` → `PrototypeApp.vue`의 실제
import 및 호출을 기준으로 확인한다. 함수가 선언되어 있거나 과거 화면에 경로가 있다는
이유만으로 연결됐다고 세지 않는다. 현재 로그인·업무 화면은 `/api/v1`의 백엔드를 거친다.

## 구현돼 있지만 실행 화면에서 호출하지 않는 API

아래 경로에는 `/api/v1` 접두사가 붙는다. 모두 삭제 대상이라는 뜻은 아니다.

| ID | API | 현재 화면과 필요한 구현 |
| --- | --- | --- |
| AUTH-04 | `GET /me` | 로그인 응답의 `me`만 사용한다. `session.refreshProfile`의 호출자는 비활성 App·PlannerSettings에만 있다. 세션 프로필·역할·메뉴 갱신을 현재 store에 연결할 필요가 있다. |
| GAP-01 | `GET /submissions/{submissionId}/comparison` | 비교 기준·대상 버전을 골라 결과를 다시 조회하는 흐름이 없다. 비교 파일 다운로드와 고정된 검토 목록 조회는 별도로 연결돼 있다. |
| GAP-03 | `GET /gap-thresholds/current` | 서버의 현행 운영 Gap 기준을 읽는 설정 화면이 없다. |
| GAP-04 | `POST /gap-thresholds/preview` | 운영 기준 변경의 영향 건수·대상을 미리 확인하는 화면이 없다. |
| GAP-05 | `POST /gap-thresholds` | 확인한 운영 기준을 저장하는 화면이 없다. 현재 계산기의 비율·금액 입력은 화면 필터이며 운영 기준 저장이 아니다. |
| UP-06 | `POST /submissions/{submissionId}/parsing-retries` | 파싱 실패 시 동일 원본을 재시도하는 버튼·상태 전이가 없다. 상태 새로고침과 검증 재실행은 이 API를 대신하지 않는다. |

업무 API 5개와 세션 API 1개, 합계 **6개**다. 우선순위는 파싱 실패 복구와 운영 Gap
기준 설정, 버전 비교, 프로필 갱신 순으로 제안한다. 이 목록은 추가 구현 요구사항이며
이슈 수정에서 해당 기능까지 구현한 것으로 표시하지 않는다.

## 보고서 연결과 남은 범위

기존 보고서 화면의 데모 의존을 줄이기 위해 `LiveReportPanel.vue`를 실제 메뉴에 연결했다.
PDF/직접 작성/저장 틀 선택 → 구성 확인 → 기간·지표 선택 → 승인 소명 분류 → 데이터
채우기·AI 편집 확인·버전 저장·내보내기를 제공한다. `report-api.js`는 RPT-01~16과 PDF
페이지 이미지 경로를 호출하며, 페이지가 있는 템플릿·지표 목록을 끝까지 읽을 수 있다.

- 자연어 조회는 RPT-11의 서버 결과를 보여주고, 사용자가 결과를 확인한 뒤 응답 SQL을 지표 사전에 등록한다.
- AI 편집안은 별도 확인 후 적용한다. 수치나 SQL을 편집 패치로 삽입하지 않으며 데이터는 다시 조회한다.
- 표는 서버 금액 문자열·병합 셀·데이터 없음 표시를 보존한다. 조회·기간·질문이 바뀌면 오래된 결과를 무효화한다.
- XLSX는 백엔드 RPT-16에서 새로 채워 내려받는다. PNG는 조회 내용을 텍스트로 렌더링하며 화면의 그림을 그대로 캡처하지 않는다. PDF는 브라우저 인쇄 저장이다.

추가 구현이 필요한 부분은 다음과 같다.

1. PDF의 임의 표·행·열을 지표/조직에 대응시키는 정밀 편집, 블록 추론·소명 요약 기능의
   공개 백엔드 계약과 Vue 연결. 현재 화면은 제목·순서·단위·기간과 기본 블록을 편집한다.
2. line/donut/waterfall 등 종류별 차트. 현재 데이터 미리보기는 조직별 막대 표시이며,
   원본 차트 디자인을 재현하지 않는다. 화면 금액 단위는 AI가 지원하는 억원·백만원이다.
3. 실제 로그인부터 PDF 작업 완료, 지표 저장, 버전 충돌, XLSX·PNG·PDF까지 브라우저와
   실행 서버를 이용한 통합 검증. 소스·계약 테스트 통과만으로 이 검증을 대체하지 않는다.
4. XLSX 숫자 타입·정밀도 정책. AI의 소수 SQL 결과는 정밀도 보존 문자열로 전달하므로
   현재 내보내기에서는 텍스트 셀이 된다. 일반 표의 `won`은 백엔드에서 double 숫자 셀로
   변환하므로 매우 큰 금액·많은 소수 자리에서 원문과 달라질 수 있다. 숫자 계산이 가능한
   범위와 원문 텍스트를 보존할 범위를 명시한 후 `ReportExportService`를 보완해야 한다.

따라서 AI 데모와 개발 경로는 즉시 삭제하지 않는다. 아직 공개 계약으로 옮기지 않은
편집·요약 기능을 확인하고 이관한 뒤 제거해야 한다.

## 고아 API로 분류하지 않는 경로

- `POST /internal/pdf-jobs/{jobId}/result`: AI 작업 완료를 받는 내부 콜백. 브라우저에서
  직접 호출하지 않는 것이 정상이다. 위 공개 API 67개에는 포함하지 않는다.
- Actuator·상태 확인: 운영·오케스트레이션 경로이며 사용자 화면 기능이 아니다.
- 옛 `source-cells`, 요청별 `template`·`forecast`·`annual-master`, `financial-values`,
  `report-values`, `auth/profile-confirmation`: 비활성 프론트의 과거 계약이다. 현 명세를
  맞추기 위해 이 서버 경로들을 새로 만들 필요는 없다.
- 옛 `/api/v1/report-authoring` 화면·표 렌더러·전용 helper는 현재 백엔드에 대응하는
  경로가 없고 활성 진입점에서 쓰지 않아 삭제했다. `PlannerReports` 호환 컴포넌트도
  현재 `LiveReportPanel`만 참조하며 별도 보고 작성 구현을 유지하지 않는다.

## 명세와 현재 배포 방식

AUTH-02 응답은 `token`, `expiresAt`, `me`이며 오류는 `INVALID_AUTH_CODE`와
`errors[].code`로 구분한다. 이 내용을 API 개요에 반영했다.
GAP-01/02는 `baseSubmissionId`만 받는다. 처리하지 않는 `unit`·`organizationId`를
문서에서 제거했다. 조직은 제출본으로 결정하고 금액은 원 단위로 제공한다.

현재 파일 저장은 로컬/PVC, 파싱은 프로세스 내 실행기, AI 분석 호출은 HTTP다.
S3·RabbitMQ·db-mcp 전환과 초안 7일/PDF 30일 자동 정리는 2차 목표다.
OpenAPI의 현재 구현 설명과 미래 목표를 구분했으며, 자동 정리가 실행된다고 안내하지 않는다.

## 검증과 제한

- 공개 API 경로 집합 양방향 대조: 67개 일치.
- 변경 관련 프론트 계약 테스트 22개 통과: 실제 ID·상태 토큰, 소명 명령, 금액·이력,
  파일 확장자, 보고서 요청·AI 패치·표·텍스트 내보내기. 파일이나 실서버를 만들지 않는다.
- 전체 `node --test src/lib/*.test.js src/prototype/*.test.js`에서는 31개 통과,
  `domain.test.js`·`navigation.test.js` 두 파일은 `pinia` 미설치로 로드 실패했다.
- CI의 기존 `npm run test:prototype`도 `src/lib` 계약 테스트를 포함하도록 확장했다.
  의존성을 설치하는 CI에서는 두 폴더의 테스트와 실제 Vite 빌드를 함께 검증한다.
- 변경된 Vue 9개를 메모리에서 parse·compileScript·compileTemplate 검사했다.
  기존 npm 캐시의 compiler-sfc 3.5.42를 읽었으며 lockfile 3.5.45와는 버전 차이가 있다.
  브라우저 배치·다운로드 검증과 구별한다. OpenAPI YAML 구문 검사도 통과했다.
- XLSB 읽기 기능은 이미 구현돼 있다. 실제 양식은 원본 검증에 통과하나 수식의 조직 조건과
  파일 소유 조직이 달라 보고 항목 매핑이 검토 필요 상태다. 동일 원본의 XLSX 짝이 없어
  XLSB↔XLSX 결과 동등성 조건은 아직 검증하지 못했다. 원본 수정으로 우회하지 않는다.

함수와 호출 관계는 [함수 명세](function-reference.md), 프론트 이슈별 변경은
[프론트 계약](frontend-issue-contract.md)을 따른다.
