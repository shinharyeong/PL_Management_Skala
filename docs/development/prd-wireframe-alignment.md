# PRD·Figma와 현재 구현 대응표

2026-11-18 기준. 현재 사용자가 지정한 **PRD v8.5**와 변경 후 소스의 대응 관계를 기록한다. 이전 작업의 “보고서 제외” 요청은 이번 PRD 비교·구현 요청으로 대체되었으며, 보고 작성과 사유유형 관리를 현재 범위에 포함한다. **연결 구현**은 화면과 실제 API 계약이 연결됐다는 뜻이며, 전체 PRD 완료나 운영 배포 검증을 뜻하지 않는다. 실행 검증은 [로컬 실행 환경](local-environment.md)의 관측 기록을 별도로 따른다.

## 확인한 원문과 적용 원칙

- PRD: [현재 PRD v8.5 기능 요구사항](https://docs.google.com/spreadsheets/d/1v87p2E0FlJAqv8VsS_sH_f8sCaQhGsPb/edit?gid=1734192708#gid=1734192708). 이전 v0.8 문서는 과거 구현의 이력이며 현재 범위 판정의 기준이 아니다. 소개의 예시 숫자보다 해당 기능 요구사항 행과 이번 사용자의 추가 지시를 우선한다.
- Figma: [경영팀을 부탁해](https://www.figma.com/design/ZW7ZlgvtY4phycygZqir3z/?node-id=2-2). 최신 경영기획 화면과 **각 조직 담당자 v3**를 기준으로 삼았다. PRD의 과거 v2 표기보다 사용자가 지정한 v3를 시각 기준으로 적용한다.
- 소명은 사용자가 요청한 두 방식 `GAP_ONLY`(Gap 초과·별도 요청)와 `ALL_CHANGES`(앞의 항목과 모든 변경 항목)를 지원한다. 전역 정책 변경 후 DRAFT는 재검증하며 완료 제출본은 당시 `comparisonContext.requirementMode/reviewPolicyId`를 보존한다. 임계값과 요구 정책은 별도 설정이다.
- 선택 조직 발송과 최초 전사 마스터 필수 집합은 별개다. 연간 최초 마스터는 전사 필수 조직 수락 후 발행하고 이후 승인 원천을 교체한다.
- 원본값·수식·조직명을 자동 보정하지 않는다. 확인된 문제 위치·값·사유를 담당자에게 보여 주고 원본 수정 후 전체 파일 재제출로 처리한다.
- 모든 API 축약 경로에는 `/api/v1` 접두사가 붙는다. 아래 Figma 노드는 확인한 화면의 근거이며 PRD의 모든 행에 별도 프레임이 존재한다는 뜻은 아니다.

상태는 **연결 구현 / 일부 구현 / 미구현**으로 구분한다. 연결 구현은 소스·API 경로의 존재와 동작 연결을 뜻하며 실운영 완료 판정이 아니다. 원문의 중복 ID·중복 설명은 ID 하나로 식별하지 않고 **기능 영역·제목·원문 위치**를 함께 본다. `FR-YEAR`·`FR-REQ`, `FR-MONTH`·`FR-GAP`의 겹치는 동작은 묶어서 기록하며 단순 FR 개수로 완료율을 계산하지 않는다.

원문에서는 `FR-NOTI-U-001/002`가 기획 알림과 조직 요청에, `FR-UPLOAD-005`가 파싱과 오류 안내에 중복 사용되며 승인 소명 이관 행은 ID가 비어 있다. 소개의 93개와 실제 95행도 일치하지 않는다. 변경 이력의 `SUBM-001~032`와 본문의 `PROOF/RESUB/HIST/UPLOAD` 분류가 혼재하므로 아래 `FR-SUBM` 묶음은 기존 대응표의 기능 추적 색인이며 현재 본문을 재번호 매긴 결과가 아니다.

### 원문 용어와 구현 단위

- `PROOF-001`의 전월 승인본과 `RESUB-005`의 같은 요청 직전 반려본은 재제출 문맥을 구분한다. 구현은 같은 요청의 직전 완료본(반려 포함)을 우선하고, 새 월의 첫 제출에 해당 기준이 없으면 전월 승인본을 사용한다. 확정 PLAN 비교는 별도 Gap 기준이다.
- `PROOF-002/006`의 모든 변경 항목과 소개의 기준 초과 항목 차이는 이번 사용자 지시에 따라 두 소명 정책으로 지원한다. `MONTH-010`의 승인 시 버전과 `PROOF-010/RESUB-007`의 제출 시 버전은 제출 회차/공식 마스터 버전을 분리한다. 제출 회차는 최종 제출 때 증가하고 승인 원천 변경은 새 마스터 버전에 반영되며, 소명 답변만으로 제출 회차가 늘지 않는다.
- 보고 항목의 “셀”은 조직·보고 항목·연월·시나리오로 식별되는 합계 칸이다. 원천 Excel 셀은 제출 ID·시트·셀 주소로 조회한다. 소명·선정·명시 비교 요청은 보고 항목 단위이고, 원천 셀마다 독립적인 승인/소명 상태를 두지는 않는다.
- 반려 항목의 `currentAmount/baselineAmount`는 보고 항목 합계이고 `sourceAmount`는 선택한 원천 한 셀의 금액이다. 합계와 단일 셀을 전후 금액으로 섞어 표시하지 않는다.
- 요청의 마감 월, 제출 파일 안의 데이터 월, 제출 회차, 공식 마스터 버전은 다르다. 예를 들어 10월 요청 파일의 12월 ESTIMATE는 10월 제출 이력에 속한다. “전월 추정”은 전월 요청의 승인본에 담긴 **같은 대상 월** 추정이며 전월 실적 금액이 아니다. 서로 다른 요청의 seq만 비교해 같은 월 버전이라고 간주하지 않는다.
- 3본 원천 비교는 명시 업무 키가 고유한 행만 대응한다. 같은 `sheet/cell`이라는 이유만으로 다른 버전의 항목이 같다고 판단하지 않는다. 임의 버전 비교를 소명으로 요청한 경우에는 그 비교 문맥을 새 소명 회차에 보존하고 기존 자동 Gap은 유지한다.

## 현재 남은 범위

운영 이메일 전달·예약 발송, 확인되지 않은 회계 분류를 포함한 전체 waterfall, 원천 셀 단위 독립 소명/승인 모델, 서버 공유 작업공간, 보고서의 임의 기간 구간·일반 LIST 계층 편집·PDF/PPTX 내보내기·편집 중 전체 undo stack은 현재 연결 범위 밖에 남는다. 운영 AI·MCP 배포 설정 및 실제 브라우저/원본 PDF 검증도 코드 존재만으로 완료 처리하지 않는다.

## 검증 범위와 변경 경계

2026-11-18 비보고서 프런트 검증은 Vue/JS script 48개 구문 검사, 공백 검사, 메모리 assertion 38개(정밀 승인원천 합산·손익 흐름·작업공간·전체 소명 이력·정책의 오래된 응답 차단과 상태 토큰)를 통과했다. 테스트는 메모리와 콘솔만 사용했다. 전체 SFC·프런트 빌드·백엔드 테스트의 최종 결과는 [로컬 실행 환경](local-environment.md)과 해당 변경의 실행 기록을 따른다. 과거 Docker healthy/Chrome 관측은 당시 화면의 이력이며 새 설정·정책·보고 기능의 브라우저 검증을 대신하지 않는다.

기존 3본 원천 비교의 9개 메모리 검사와 실제 제출 API 읽기 기록은 [프런트 구현](frontend-guide.md) 및 로컬 실행 기록에 유지한다. 명시 키 누락·중복, 좌표 이동, 소수 6자리·안전정수 초과 금액, 부분 적재·0/누락을 구분한 범위의 검증이며 모든 원본 파일의 적합성 증명은 아니다.

Figma와 PRD 원본, Data/ 원본 데이터, 과거 확정 비교·제출 기록을 수정하지 않았다. 요청·제출·승인·양식 등록·첨부·다운로드는 명시 사용자 동작으로 실행하며 화면 점검만으로 최종 제출·승인을 자동 실행하지 않는다. 소스 함수·호출 관계는 [프런트 구현](frontend-guide.md), 서버 계약은 [API 명세](api-contract.md)를 따른다.
